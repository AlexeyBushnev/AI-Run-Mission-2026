# ADR-002: Use Kafka eventing with the Outbox pattern for cross-service ordering and inventory propagation

## Context
Meridian Phase 1 must support strangler-fig coexistence across new commerce services and legacy enterprise systems. The architecture needs clear service boundaries that survive future phases, and the biggest reversal risk is that a coding agent quietly reintroduces direct synchronous calls between Cart, Checkout, and inventory-related services.

## Decision
We will use Kafka-based eventing with the Outbox pattern for cross-service ordering and inventory propagation between Meridian Phase 1 services and downstream projections.

## Alternatives Considered
1. **Direct synchronous service-to-service calls** — rejected because this would tighten runtime coupling, increase cascade-failure risk, and make the strangler-fig cutover harder to manage across evolving service boundaries.
2. **Database-level integration / shared database signaling** — rejected because it hides service boundaries, increases coupling at the data layer, and makes independent service evolution harder during the staged migration.

## Consequences
- **Positive:** Supports loose coupling, event-driven projections, cache warm-up, and more resilient cross-service communication for Phase 1 and beyond.
- **Negative:** Adds event delivery, replay, ordering, and observability complexity that the internal team must learn to operate safely.

## Agent-Readable Summary
All cross-service ordering and inventory events must transit Kafka using the Outbox pattern from the service that owns the state change. Do not introduce direct synchronous runtime calls between Cart, Checkout, and inventory-projection paths where an event-driven boundary has been defined.
